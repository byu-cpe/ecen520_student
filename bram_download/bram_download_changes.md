## Top-level behavior: missing or ambiguous specification

- [x] **Button interaction with a single transmitter.** Both buttons drive the one UART transmitter. "Ignore any button presses … until the entire ROM has been sent" doesn't say whether a *right* press during a ROM send is also ignored. Recommend: while either send is in progress, ignore both buttons. *Resolved:* added a bullet stating that both sends share the transmitter and that presses of both buttons are ignored while either send is in progress; removed the two per-button "ignore" sentences.
- [ ] **How to resend the ROM.** The testbench presses the left button twice to see the fight song twice. Say that the ROM's `init` input should be pulsed at the start of each send, so the pointer returns to 0.
- [ ] **When does a ROM send end?** Tie it explicitly to `rom_end` from the bram lab. It is asserted when the ROM output is zero, so the zero byte is not transmitted. This also answers the student feedback asking for `rom_end` to be exposed (it can drive the LED[2] "ROM busy" logic).
- [x] **"Flow control" is the wrong term.** "You will need to implement flow control so that you don't send another character until the previous character has been sent" describes waiting on the transmitter's busy signal, not UART flow control (RTS/CTS). Rephrase to "wait until the transmitter is no longer busy before sending the next character." *Resolved.*
- [x] **FIFO full behavior:** say that characters received while the FIFO is full are dropped (the FIFO ignores writes when full). *Resolved.*
- [ ] **FIFO read timing:** depends on the `dout` timing decision still open in `../bram/bram_changes.md`. Once that's settled, say here when to sample `dout` relative to `re`.
- [x] **Reset and buttons:** the md doesn't mention them; restate the rx_download requirements:
  - `CPU_RESETN` is active-low and goes through a two-flip-flop synchronizer.
  - Each button needs a synchronizer (with `ASYNC_REG`), a debouncer, and one-shot logic.
  - *Resolved:* the Top-Level Design bullets now require the `CPU_RESETN` two-flip-flop synchronizer (low asserted). For `BTNL` and `BTNR` they require a synchronizer with `ASYNC_REG` on the first flip-flop, a debouncer using `DEBOUNCE_TIME_US`, and one-shot logic. The UART bullet also points back to rx_download's RX synchronizer and TX output flip-flop.
- [x] "send each character received in the BRAM over the UART" → "in the BRAM FIFO". *Resolved* (same sentence as the button-interaction fix).
